# 文档先行开发规范

## 1. 目标

本规范用于保证 `简单生活` 项目在多人或多 agent 并行开发时，依然能保持：

- 业务边界一致
- 接口理解一致
- 多端体验一致
- 交付节奏可控

## 2. 基本原则

1. **先文档，后实现**：没有文档定义的需求，不进入编码阶段
2. **先契约，后联调**：没有接口契约和字段说明，不进入联调阶段
3. **先评审，后变更**：影响多端或多服务的变更，必须先完成文档评审
4. **单一事实来源**：同一业务规则只能有一份主文档

## 3. 文档层级

```text
产品文档 -> 服务文档 -> 接口文档 -> 页面文档 -> 验收文档
```

各层级职责如下：

- **产品文档**：定义目标、边界、用户流程、核心能力
- **服务文档**：定义服务职责、依赖、输入输出、业务边界
- **接口文档**：定义请求、响应、字段、错误码、示例
- **页面文档**：定义页面结构、状态、交互、埋点
- **验收文档**：定义完成标准和验收口径

## 4. 功能开发前置条件

任何新功能开始之前，必须至少具备以下内容：

- 需求目标
- 用户流程
- 页面结构
- 接口说明
- 字段字典
- 验收标准

如果缺失其中任一项，默认不允许进入实现阶段。

## 5. 服务文档模板

每个业务服务都必须维护以下文档：

```text
services/<service>/docs/
├── README.md
├── api.md
├── pages.md
├── data-model.md
├── workflow.md
└── changelog.md
```

与之对应的实现目录建议为：

```text
services/<service>/
├── proto/
├── src/
├── tests/
└── BUILD.bazel
```

### `README.md`

- 服务目标
- 服务边界
- 不负责什么
- 上下游依赖
- 核心能力列表

### `api.md`

- 接口名称
- 接口说明
- 请求字段
- 响应字段
- 错误码
- 示例请求与响应

补充约束：

- `gateway/api.md` 维护对外 HTTP/JSON 契约
- 业务域 `api.md` 维护内部 `proto` / RPC 契约
- `api.md` 必须做到自包含，阅读时不依赖先翻其他文档才能理解消息结构
- 示例格式、共享样例 ID、时间戳写法等统一约定见 `docs/examples/README.md`

### `pages.md`

- 客户端页面入口
- 页面状态
- 页面依赖接口
- 空态、异常态、加载态

### `data-model.md`

- 核心实体
- 字段含义
- 枚举定义
- 字段是否必填

### `workflow.md`

- 业务主流程
- 异常流程
- 服务调用关系

### `changelog.md`

- 契约变更内容
- 变更影响范围
- 兼容性说明

## 6. 并行开发协作模型

### 客户端

客户端依据以下文档独立开发：

- 产品文档
- 页面文档
- 接口文档
- mock 数据

### 服务端

服务端依据以下文档独立开发：

- 服务 README
- 数据模型
- workflow
- API 文档

### 协议约束

为保证多端与多服务协作稳定，本项目采用统一协议边界：

- 客户端与承担 BFF 职责的 `gateway` 的接口文档使用 JSON 语义描述
- 服务内部接口文档和 RPC 契约使用 `proto` 描述
- 客户端不直接依赖内部服务 `proto`
- JSON 与 `proto` 的协议映射由 `gateway` 负责

文档编写时应遵守以下规则：

- 面向客户端的 `api.md`、页面文档、mock 数据以 JSON 结构为准
- 面向服务内部联调的接口和消息结构以服务 owner 维护的 `proto` 为准
- 若 JSON 字段语义与 `proto` 字段语义冲突，以已评审的公共契约和服务契约为准，必须同步修正
- 服务代码、`proto`、测试与构建配置统一落在 `services/<service>/` 下，不再额外拆出独立 `server/` 总目录

### 测试

测试依据以下文档并行准备：

- 用户流程
- 接口文档
- 验收标准
- 异常场景说明

## 7. 变更规则

### 小变更

不影响外部契约的小变更，可以直接改实现，但必须同步更新相关文档。

### 中变更

影响页面字段、接口字段、错误码或交互流程的变更，必须先修改文档，再通知相关端开发。

### 大变更

影响多个服务、多端页面或核心业务流程的变更，必须先完成文档评审，再安排开发。

## 8. 版本管理规则

- 文档与代码必须同版本演进
- 接口 breaking change 必须显式记录在 `changelog.md`
- 已经被客户端使用的字段，禁止静默删除或变更语义
- 重要枚举和值域变更必须同步所有终端
- JSON 契约与内部 `proto` 契约变更时，必须同步检查 `gateway` 的映射层

## 9. Definition of Done

一个功能只有同时满足以下条件，才算真正完成：

- 文档已更新
- 接口已实现
- 页面已接入
- 验收标准已满足
- 关键流程可回归

## 10. 适配 AI 并行开发

本项目允许多 agent 并行协作，但必须遵守如下约束：

- 每个 agent 只负责一个明确服务目录（包括 `gateway` 或某个业务域）或一个明确文档任务
- agent 之间共享的信息来源必须是文档，而不是口头约定
- 如果接口文档和代码实现冲突，以已评审文档为准，代码必须回调修正

## 11. 结论

文档在本项目里不是辅助材料，而是协作协议、系统边界和开发入口。

只有坚持 `文档先行`，项目才能在多端、多服务、多 agent 并行开发时保持稳定、清晰和可扩展。
