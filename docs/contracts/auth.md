# 鉴权与用户态约定（Auth）

## 1. 目的

从**契约层**描述终端与网关/业务服务之间的身份凭证与用户态，不涉及具体算法与密钥存储实现；适用于 Web、iOS、Android、各厂商小程序。

## 2. 身份模型

| 概念 | 说明 |
|------|------|
| **访客（guest）** | 无账号体系下的匿名用户，仍可有会话与设备标识 |
| **登录用户（authenticated）** | 已绑定账号（手机号、三方 OAuth 等，具体由 user-domain 实现） |
| **凭证（credential）** | 用于证明当前请求所属用户或访客会话 |

## 3. HTTP 头约定

| 头名称 | 必填 | 说明 |
|--------|------|------|
| `Authorization` | 按接口定义 | 推荐：`Bearer <access_token>`；仅允许服务端签发的令牌 |
| `X-Request-Id` | 否 | 客户端可生成并传入，便于与 [common-response.md](./common-response.md) 的 `meta.request_id` 对齐；若网关覆盖以服务端为准 |
| `X-Client-Platform` | 推荐 | 枚举小写字符串，如 `web`、`ios`、`android`、`wechat_miniprogram`、`douyin_miniprogram` |
| `X-Client-Version` | 推荐 | 应用语义化版本，如 `1.4.2` |
| `X-Device-Id` | 推荐 | 稳定设备标识（由各端按隐私合规生成）；用于访客归因与风控，**不得**当作唯一安全凭据 |

具体接口可额外要求 `X-App-Id` 等，须在接口文档列出。

## 4. 令牌类型（逻辑角色）

| 令牌 | 典型用途 | 生命周期 |
|------|----------|----------|
| `access_token` | 访问受保护 API | 短效 |
| `refresh_token` | 换取新的 `access_token` | 长效，可撤销 |

契约要求：

- 传输仅通过 `Authorization: Bearer` 或接口文档明确的安全通道（如 HTTPS POST body），**禁止**在 URL query 中长期携带刷新令牌。
- 失效时返回 [error-codes.md](./error-codes.md) 中 `20002` / `20003` 等，由客户端走刷新或重新登录。

## 5. 用户态在响应中的体现（可选）

部分接口可在 `data` 中返回轻量用户摘要，字段名建议统一：

| 字段 | 类型 | 说明 |
|------|------|------|
| `user_id` | string \| null | 登录用户 ID；访客为 `null` |
| `is_guest` | boolean | 是否为访客会话 |

**禁止**在通用契约中强制所有接口返回完整画像；详细结构由 user-domain 接口单独定义。

## 6. 权限与数据范围

- **鉴权通过**仅表示「知道你是谁」，具体资源是否可读由内容与治理策略决定（可能返回 `30002`、`60001` 等）。
- 多端必须使用相同错误码语义，避免一端 403 另一端空数据且无码。

推荐职责分工：

- `gateway` 负责入口层身份校验、令牌解析或向 `user-domain` 发起会话校验，并把标准化用户上下文注入下游请求
- 各业务域负责资源级与业务级授权判断，不把业务权限规则硬编码在 `gateway`

## 7. 小程序补充

- 可将平台侧 `openid` 等与内部 `user_id` 的映射完全放在服务端，客户端契约层只暴露 `access_token` 与上述标准头。
- `X-Client-Platform` 须能区分不同小程序宿主，便于统计与渠道策略。

## 8. 兼容性

新增令牌类型或头字段须向后兼容：旧客户端忽略未知头；服务端对缺省头应有合理降级（须在接口文档说明）。
