# user-server

## 定位

`user-server` 是一个**通用的用户管理服务**，提供用户全生命周期管理能力：注册、登录、鉴权、个人信息、偏好、收藏、浏览历史、反馈、隐私同意等。

本服务以 **API-first** 原则设计，不依赖特定前端或业务场景。公司内任意应用均可接入，复用同一套用户管理能力，无需重复建设。

## 设计原则

| 原则 | 说明 |
|------|------|
| **通用性** | 不绑定特定业务域或内容类型；内容引用使用通用 `content_id` + `content_type` 模式，收藏/历史等能力适用于任意内容 |
| **前端无关** | 通过内部 RPC 对外提供服务，客户端通过 API 网关访问；服务本身不感知前端实现细节 |
| **多应用支持** | 同一套服务可支撑多个应用的客户管理需求，通过 `app_id` 命名空间隔离数据与配置 |
| **可扩展** | 认证方式、内容类型、信号消费者等均可按需扩展，无需修改核心逻辑 |
| **契约驱动** | 对外以 proto 契约为准，实现细节（token 编码、存储选型等）为 provider-owned，调用方不依赖 |

## 核心能力

| 能力域 | 说明 |
|--------|------|
| **账号与认证** | 用户注册标识、账号状态、多种登录方式（手机 OTP、OAuth 等） |
| **会话与令牌** | 签发/轮换/撤销 access/refresh token；令牌内省供网关鉴权 |
| **个人资料** | 昵称、头像、语言、简介、通知偏好 |
| **用户偏好** | 主题/分类/排序偏好，版本化存储，支持乐观并发控制 |
| **收藏** | 通用内容收藏，支持任意内容类型引用 |
| **浏览历史** | 用户可见的浏览记录摘要，支持去重聚合与按时间清理 |
| **反馈** | 结构化反馈（评分、原因、文本），关联用户或会话 |
| **隐私同意** | 个性化/分析/营销开关，合规版本管理 |
| **个性化信号** | 为下游服务（推荐、搜索等）提供信号引用，受同意状态门控 |

## 边界

### 属于本服务

| 领域 | 职责 |
|------|------|
| 账号 | 用户注册标识、账号状态、登录绑定元数据 |
| 会话与令牌 | 签发/轮换/撤销令牌；令牌内省（有效性、user_id、过期时间等） |
| 资料 | 展示名、头像引用、语言、简介、通知开关 |
| 偏好 | 分类/兴趣选择，作为推荐等下游服务的输入（不含排序逻辑） |
| 收藏 | 保存的内容引用（通用 content_id）及时间戳 |
| 历史 | 浏览/曝光摘要（用户可见状态，非原始点击流——原始事件由追踪服务负责） |
| 反馈 | 结构化反馈记录（评分、原因码、自由文本） |
| 同意 | 个性化/分析/营销标志；暴露给网关及下游服务作为门控信号 |
| 信号引用 | 预计算信号束的引用（signal_bundle_ref）——不含排序、召回或模型执行逻辑 |

### 不属于本服务

| 关注点 | 归属 |
|--------|------|
| 推荐召回、排序、策略、解释 | 推荐服务 |
| 内容正文、编辑工作流 | 内容服务 |
| 点击追踪、归因管道 | 追踪服务 |
| 审核决策、内容下架 | 治理服务 |
| 对外 HTTP 路径、JSON 字段名 | API 网关 + 契约文档 |

## 多应用架构

本服务设计为多应用共享，核心机制：

- **应用标识**：每个接入应用分配唯一的 `app_id`，用于命名空间隔离
- **数据隔离**：收藏、历史、偏好等用户数据按 `app_id` 隔离；账号与会话可跨应用共享或独立，由配置决定
- **认证配置**：各应用可启用不同的认证方式（如 A 应用仅支持手机 OTP，B 应用仅支持 OAuth）
- **同意策略**：隐私同意策略可按应用定制（如不同地区的默认值与合规要求）
- **内容类型**：各应用可注册自己使用的内容类型枚举值，收藏/历史等能力自动适配

### 接入新应用的流程

1. 在服务配置中注册 `app_id` 及其认证方式、同意策略等
2. 网关配置该应用的路由与鉴权规则
3. 应用通过网关调用本服务 API，`app_id` 由网关注入请求上下文
4. 如需新的内容类型，在 `ContentRefType` / `FavoriteContentType` 枚举中追加值

## 依赖

### 上游（消费）

- 身份提供方 / OTP / OAuth 适配器（实现细节，不在公共契约中建模）
- 可选：异步任务或特征管道写入本域读取的信号数据（数据模型仍由本域拥有）

### 下游（消费方）

- **API 网关**：鉴权、资料、收藏、历史、反馈、同意；注入用户上下文到下游请求
- **推荐/搜索等下游服务**：消费同意标志和信号引用
- **任意接入应用**：通过网关访问用户管理能力

### 对等协作

- **追踪服务**：可能产生事件流入历史或反馈分析；本域存储用户可见或偏好相关的聚合数据，非完整原始事件
- **治理服务**：可能影响历史/收藏返回哪些内容（如已下架内容 ID）；默认由网关或内容读取链路过滤不可见内容，本域仅返回自身持有的用户状态与引用

## 非目标

- 存储完整内容正文或编辑工作流
- 计算推荐分数或运行排序模型
- 生成追踪或归因 URL
- 替代统一的权限/角色管理系统（RBAC 等属于独立关注点）

## 服务等级目标（SLO）与容量假设

本域是**鉴权关键路径**：`IntrospectAccessToken` 处于每个登录请求的同步链路上，可用性目标高于一般读接口。指标针对服务端处理耗时（不含网关与网络往返）。

| 指标 | 目标（v1） |
|------|-----------|
| 鉴权可用性（`IntrospectAccessToken` / `IntrospectRefreshToken`） | ≥ 99.95% |
| 鉴权延迟（命中 Redis 会话缓存） | P50 ≤ 5ms，P99 ≤ 20ms |
| 鉴权延迟（回源 PostgreSQL） | P99 ≤ 50ms |
| 登录签发（`IssueTokenPair`） | 可用性 ≥ 99.9%，P99 ≤ 150ms（不含外部 OTP/OAuth 校验耗时） |
| 用户态读（`GetProfile`/`GetMeSummary`/`ListFavorites`/`ListHistory`/`GetConsent`） | 可用性 ≥ 99.9%，P50 ≤ 15ms，P99 ≤ 80ms |
| 用户态写（`UpdateProfile`/`UpdatePreferences`/`AddFavorite`/`RecordHistoryEvent`/`UpdateConsent`） | P99 ≤ 120ms |
| 同意变更生效（`UpdateConsent` 到下游读到新标志，含缓存失效） | ≤ 2s |
| `signal_bundle_ref` 解析（`ResolveSignalBundle`） | P99 ≤ 60ms |

容量假设（v1，单写权威 + 只读副本/缓存扩展）：

| 维度 | 假设 |
|------|------|
| 账户规模 | ≤ 100 万级 |
| 活跃会话 | ≤ 50 万并发会话 |
| 鉴权 QPS（内省合计） | ≤ 2000 QPS |
| 用户态写 QPS | ≤ 100 QPS |
| 单用户收藏 / 历史保留行数 | 收藏不设硬上限（建议软提示）；历史按保留窗口滚动（见 [data-model.md](./data-model.md) §16.2） |

超出假设时优先扩展 Redis 会话/同意缓存与 PostgreSQL 只读副本承接内省与读路径；令牌签发、撤销与偏好乐观锁写入保持单写权威，不做多主。
